# PR 작성 규칙

PR은 검토자가 대화 내용을 읽지 않아도 문제·변경 결과·검증 범위를 이해할 수 있도록 작성한다. 본문은 저장소의 [PR 템플릿](../../.github/pull_request_template.md)을 사용한다.

## 제목

- [커밋 규칙](commit.md)의 `type: 변경 요약` 또는 `type(scope): 변경 요약` 형식을 사용한다. 요약은 한국어로 작성한다.
- 제목은 PR 전체의 최종 변경을 설명한다. 여러 커밋이 있으면 마지막 커밋의 제목을 그대로 쓰기보다 변경의 주된 목적에 맞게 정한다.
- 브랜치 접두사와 커밋 개수는 타입 선택의 기준으로 삼지 않는다. 관련 이슈가 실제로 있을 때만 번호를 기재한다.

## 본문

| 항목 | 작성 내용 |
| --- | --- |
| 변경 목적 | 어떤 문제나 부족한 부분을 해결하며 변경 후 무엇이 달라지는지 |
| 주요 변경 사항 | 최종 구현의 핵심 동작·책임·구조. 단순 변경 파일 나열은 피함 |
| 영향 범위 | 모듈 의존성, 공개 API, navigation·상태 관리, Gradle convention, 문서 경로 등 검토에 필요한 영향. 해당 없으면 `없음` |
| 검증 | 실제 실행한 명령과 결과, 테스트 개수·실패 여부, 캐시 결과 재사용 여부, 미실행 이유와 남은 범위 |
| 참고 사항 | 리뷰 시 확인할 부분, 관련 문서·이슈, 후속 확인. 없으면 생략 가능 |

- 조회 인자나 오류 상태처럼 동작이 바뀌면 필요한 경우 구체적인 변경 전·후 예를 든다.
- 검증은 [품질 규칙](quality.md)을 따른다. `NO-SOURCE`를 테스트 통과로, Android test APK 빌드를 기기 테스트 통과로 보고하지 않는다. 컴파일로 확인한 DI 연결과 실제 화면·복원 검증도 구분한다.
- 대화의 작업 순서나 중간 시도를 나열하지 않고 최종 변경을 기준으로 작성한다. 보류한 설계 변경이 현재 구현처럼 읽히지 않도록 한다.
- 문서 링크는 최종 저장소 경로를 사용한다. 개인 컴퓨터의 절대 경로를 PR의 필수 참고 링크로 넣지 않는다.

## 제출 전

- 원격 저장소의 기본 브랜치 또는 사용자가 지정한 대상 브랜치를 확인한다. head는 이번 작업 브랜치로 지정한다.
- base와 head의 전체 차이를 확인하고 PR에 포함되는 커밋·파일이 요청 범위에 맞는지 확인한다. 기존 사용자 변경은 커밋에서 제외한다.
- 같은 브랜치의 열린 PR이 있는지 확인한다. 있으면 기존 PR의 제목·본문을 최종 변경에 맞춰 갱신한다.
- 구현이 완료되고 가능한 검증을 마치면 일반 PR로 제출한다. 구현 중이거나 설계 합의를 먼저 받을 목적이면 Draft로 표시한다. 기기 부재 등으로 남은 검증은 본문에 명시한다.
- 커밋·푸시·PR 생성은 사용자가 요청한 범위에서 수행한다. PR 작성 규칙을 추가한 것만으로 제출이나 병합을 실행하지 않는다.
