# 커밋 메시지 규칙

기존 저장소의 `feat:`, `refactor:`, `ci:` 형식을 이어서 사용한다. 이 문서는 이후 작성하는 커밋의 기준이며, 과거 커밋 메시지를 변경하지 않는다.

## 메시지 형식

```text
type: 변경 요약
type(scope): 변경 요약
```

- `type`은 아래 표의 영문 소문자를 사용한다.
- 요약은 한국어로 간결하게 작성하고, 변경된 동작이나 목적이 드러나도록 한다. `수정`, `정리`, `작업 완료`만 적지 않는다.
- `scope`는 선택 사항이다. `youtube`, `bookmark`, `navigation`, `data`, `build-logic`처럼 영향을 받는 영역이 명확할 때 사용한다.
- 커밋 타입은 실제 변경 내용으로 정한다. 브랜치가 `refactor/…`라고 해서 문서나 테스트 커밋까지 `refactor`로 작성하지 않는다.

## 타입 선택

| 타입 | 용도 |
| --- | --- |
| `feat` | 사용자 기능 추가 또는 새로운 동작 제공 |
| `fix` | 잘못된 동작이나 오류 수정 |
| `refactor` | 외부 동작을 유지하면서 구조·책임·구현 방식 개선 |
| `test` | 테스트와 테스트 전용 도구·예제 추가 또는 수정 |
| `docs` | 문서와 작업 계획 추가 또는 수정 |
| `build` | Gradle, dependency, convention plugin 등 빌드 구성 변경 |
| `ci` | CI workflow 변경 |
| `chore` | 위 타입에 해당하지 않는 저장소 관리 작업 |

## 본문과 이슈

- 제목만으로 설명이 충분하면 본문을 생략한다.
- 설계 결정이나 호환성 영향이 있으면 빈 줄 뒤에 변경 이유, 영향, 필요한 후속 작업을 적는다.
- 검증 내용을 적을 때는 실제 수행한 명령과 결과를 사용한다. 실행하지 않은 검증은 `미실행`으로 표시한다.
- 관련 이슈가 실제로 있을 때만 본문에 번호나 링크를 남긴다. 브랜치명에서 임의의 번호를 만들거나 특정 회사의 이슈 시스템을 기본값으로 가정하지 않는다.

## 변경 묶음

- 하나의 커밋은 관련된 하나의 목적을 담는다. 구현과 그 구현에 필요한 테스트·문서는 같은 변경 묶음에 포함할 수 있다.
- 독립적인 문서 준비, 빌드 설정, 구현, 테스트 작업은 검토 가능한 단위로 나눌 수 있다. 파일마다 커밋을 나누지는 않는다.
- 커밋 전 실제 diff와 staged 파일을 확인하고, 요청 범위 밖의 기존 사용자 변경을 포함하지 않는다.
- 커밋 메시지 규칙을 추가한 것만으로 커밋·푸시를 실행하지 않는다. 사용자가 요청한 범위에서 수행한다.
- PR 제목과 설명은 [PR 규칙](pull-request.md)과 저장소의 [PR 템플릿](../../.github/pull_request_template.md)을 따른다.

## 예시

```text
docs: 테스트 예제 보강 계획과 커밋 규칙 추가
build: 공통 coroutine 테스트 의존성 등록
test: 공통 Fake repository와 MainDispatcherRule 추가
refactor(bookmark): 화면 인자를 AssistedFactory로 전달
refactor: 화면 문자열을 리소스로 분리
test(youtube): 최초 조회와 오류 후 재시도 검증
```
